# iam-platform-poc

Private proof of concept for a new IAM/IGA platform. Design choices come from the architecture document
(stack: Angular, NestJS, Rust core, Dolt for versioned business data). No license has been granted for
redistribution.

Docs: [local setup (start here)](docs/local-setup.md), [usage](docs/usage.md), [end-to-end tests](docs/e2e.md), [plugin contract](docs/plugin-contract-v0.md).

## Hosted demo (free tier)

A live fictional demo runs on a free Render web service: <https://iam-poc-demo.onrender.com>
(sign in as `demo-alice` / `demo-only-not-a-secret`; fictional users and data only).
Free-tier limits: the instance sleeps after 15 min idle (cold start ~1 min), and
every wake re-seeds the data. Full details, limits, deploy-your-own on any branch,
and the GitHub Codespaces branch demo: [docs/demo.md](docs/demo.md).

## Real vs simulated
- Real in the end-to-end test: the Rust core binary (Cedar decisions) and the NestJS HTTP API.
- In-memory stand-ins (simulated): the activation journal (target: PostgreSQL), plugin effects (nothing is sent).
- PostgreSQL: the activation journal is durable when `IAM_PG_URL` is set (per-tenant advisory lock for seq). Tested on a real PostgreSQL server started without Docker by `src/pg.e2e.spec.ts` (`PG_BIN=<dir with initdb+postgres>`, e.g. `npm i embedded-postgres` then `node_modules/@embedded-postgres/linux-x64/native/bin`; skipped with a message otherwise). Not tested: the compose PostgreSQL service, a separate runtime-vs-IAM database split, crash recovery.
- NATS: `NatsService` publishes `iam.activation.<tenant>` to JetStream stream IAM_EVENTS after the journal commit when `IAM_NATS_URL` is set. Tested against a real `nats-server` binary (`NATS_SERVER_BIN`, no Docker): consumer receives the event; unreachable NATS gives `event: "not-published"` while the activation still succeeds; disabled by default. Outbox: see the activation protocol bullet. Consumer: `integrations/activation-consumer.ts` dedupes on (tenant, seq) in PostgreSQL `processed_events`, in the same transaction as the handler (handler failure = rollback and retry on redelivery); tested with duplicate delivery, a failing handler and duplicate NATS publication. Delivery stays at-least-once (a lost ack after publish can duplicate before `sent_at`); an EXTERNAL effect is only safe if the target also dedupes on the key `tenant:seq` passed to the handler (a crash after the effect and before the commit re-runs the handler). No real external effect is wired to this consumer yet. NOT done: other consumers/subscribers in the platform, the compose NATS service.
- OpenBao: `SecretsService` reads KV v2 (`secret/data/<path>`) with a token when `IAM_BAO_ADDR`/`IAM_BAO_TOKEN` are set; the journal's PostgreSQL URL can come from `secret/iam/pg` (field `url`). Tested against a real `bao server -dev` binary (`BAO_BIN`, dev mode, fictional local token): read, missing, bad token. The journal-from-OpenBao wiring is tested with a stubbed secret store only. NOT done: AppRole/other auth, renewal, transit/PKI, production unseal/storage.
- Temporal: `POST /tenants/:t/activation-workflows` runs an activation as a Temporal workflow (`src/temporal/`): activity `verifyCommit` (commit reachable from Dolt main, retried) then activity `record` (journal + core apply + event; retried, idempotent per `requestId`). Enabled by `IAM_TEMPORAL_ADDR`; in-process worker, task queue `iam-activation`. Tested against a real `temporal server start-dev` binary (`TEMPORAL_BIN`, no Docker) with real Dolt: success twice (seq 1,2), unknown commit fails the workflow and nothing is journaled. NOT done: crash-recovery/compensation, signals/queries/versioning, TLS/auth, a standalone worker process, the compose Temporal service (which also needs its PostgreSQL).
- CSV connector: `POST /tenants/:t/connectors/csv` (HR-style CSV -> Dolt branch -> SoD simulation, merge is explicit). Tested with real Dolt (clean import, SoD conflict, malformed input). Second connector: `POST /tenants/:t/connectors/scim`, a SCIM 2.0-LIKE subset (ListResponse-shaped `Resources`, userName, displayName, active, roles, enterprise extension department/manager), same branch + SoD flow, tested with real Dolt (inactive and role-less users skipped, SoD conflict unmergeable, injection-style input 400). It is NOT a SCIM server (no /Users endpoints, PATCH, filters, pagination, groups). No LDAP/database connectors.
- Angular console (`apps/web`): sign-in with PKCE (token kept in memory), assignments, simulate, merge, activate. Unit tests pass (PKCE test vector, API client with a FAKE fetch, render). `scripts/ui-e2e.mjs` drives the console in headless Chrome (playwright-core) against the REAL Dolt, core and API started locally on 127.0.0.1: wrong password rejected, login, SoD violation shown and merge refused (409 message), clean change merged, activation journaled; 4 screenshots were visually inspected. Needs `DOLT_BIN`, `CHROME_BIN`, `npm i playwright-core`. Not covered: other browsers, accessibility, responsive layout.
- Activation protocol (`src/activation/`, tested in `src/activation.e2e.spec.ts` on real Dolt + real core, in-memory journal): enabled when `IAM_CORE_URL` and `IAM_CORE_ADMIN_TOKEN` (same value as the core's, min 8 chars) are set. Steps: journal row `pending` (state column in PostgreSQL), export Dolt data AS OF the commit, `POST /v1/activate` to the core, mark `applied` or `failed` (HTTP 502 with the error), Dolt tag `act-<tenant>-<seq>`, NATS event only when applied, through a PostgreSQL outbox (row written in the same transaction as the `applied` state, `relay()` publishes in order and marks `sent_at` after the NATS ack: at-least-once, consumers must dedupe on tenant+seq; unsent rows survive an API restart and NATS outage; PostgreSQL + core-apply mode only, otherwise the event is published directly). Idempotence is per client-supplied `requestId` (body field, 8-64 chars [A-Za-z0-9_-], unique per tenant): the same request retried returns the same activation (same seq, no new effect; a failed/pending one is re-applied under the same seq), the same request id with another commit is refused. Without a request id, or with a new one, every call is a NEW activation with a new seq, even for a commit activated before (A -> B -> A = 3 seqs, tested on real PostgreSQL and on real Dolt + core). `POST /tenants/:t/activations/reconcile` re-applies the latest activation when the core runs another version (e.g. restarted). Tested: apply changes real decisions, SoD computed by the core, double apply, core down -> failed -> retry, core restart -> reconcile, token required, stale seq refused. Background loop: when `IAM_RECONCILE_INTERVAL_MS` (>= 200) is set, the API relays pending outbox events and reconciles every tenant periodically (PostgreSQL journal only; tested: a restarted core without state dir gets its version back, by `tick()` and by the timer). NOT done: leader election for several API instances, crash recovery of the API between journal and apply other than by calling activate/reconcile again, automatic reconcile loop, PostgreSQL variant of the activation tests (journal state column is written but only tested in-memory), The Temporal workflow now passes `requestId` (workflow id `activation-<tenant>-<requestId>`) and `record` is retried safely because the journal is idempotent per requestId.
- Signed plugin packages (core, `crates/iam-core/src/package.rs`): `IAM_PLUGIN_PACKAGE=<dir>` (manifest.json, manifest.sig = Ed25519 over the exact manifest bytes, plugin.wasm) and `IAM_PLUGIN_TRUSTED_KEYS=<base64url pubkeys, comma-separated>`. The core refuses to start unless the signature verifies under a trusted key, abi is `decide-v0` and the wasm SHA-256 equals the signed one. Setting both `IAM_PLUGIN_PACKAGE` and the unsigned dev variable `IAM_PLUGIN_WAT` is refused. Tested: valid package loads and runs, tampered wasm, tampered manifest, untrusted/missing key, signed wrong abi; refusal of a bad package also checked by hand on the binary. NOT done: signing CLI (tests use a demo key), key rotation/revocation, per-tenant enablement from Dolt, publishing/distribution, async (NestJS) plugin packaging.
- gRPC (Decide only): IMPLEMENTED for the decision path. The core serves `iam.decision.v1.Decision/Decide` with tonic when `IAM_CORE_GRPC_ADDR=host:port` is set (opt-in; proto compiled with the pure-Rust `protox`, no protoc needed; same decision code as HTTP `/v1/decide`, `tenant` field added to the proto). NestJS `POST /access/check` uses `@grpc/grpc-js` when `IAM_CORE_GRPC_ADDR` is set, HTTP otherwise; both fail closed. Tested: Rust unit test over a real socket, `grpc.e2e.spec.ts` against the real core binary (gRPC answer = HTTP answer, tenant mode fail closed then activated). Still OPEN: gRPC for `/v1/activate` and the IdP endpoints (HTTP only), TLS and caller auth on the gRPC port (plaintext loopback, do not expose), streaming, generated typed client in NestJS (proto-loader is dynamic). Ran in CI run #5 (api job).
- Dolt: the NestJS API reads/writes a real Dolt SQL server (mysql2): `GET /tenants/:t/assignments`, `POST /tenants/:t/changes` (creates a branch, simulates the role assignment, SoD check, commit on the branch), `POST /tenants/:t/changes/:branch/merge` (re-checks SoD, 409 if violated, merges into main); activation records the Dolt main commit hash. Covered by `src/dolt.e2e.spec.ts` (starts `dolt sql-server` on a temp copy; skipped with a message if `dolt` is missing; set `DOLT_BIN`). Dolt was run without Docker; the compose Dolt service was not.
- Compose: validated in CI run #5 (final version, commit fa41806): the `compose` job ran the 5 container-level checks AND `compose-app.e2e.spec.ts` (1/1, not skipped, 0 failed) on the real containers: Dolt container -> export -> activation -> PostgreSQL container journal+outbox -> Rust core (local process built by the job, gRPC decision) -> NATS container -> idempotent consumer. Before CI the same spec had passed locally only against local stand-in processes. The core has no container image yet (OPEN).

## Which slice of the design is built (POC scope statement)
Realised and tested: Dolt data versions with branch/SoD simulation/merge, activation of a Dolt commit into the Rust core (idempotent per request id, persisted, reconciled), Cedar decisions in the core with roles and SoD taken from the activated data, signed WASM plugin package verification, PostgreSQL journal and outbox, NATS event with an idempotent consumer, Temporal activation workflow, OpenBao secret read, CSV and SCIM-LIKE ingestion connectors, Angular console, gRPC for `Decide`.
Slice 1 of the follow-up work is built: persistent DECISION AUDIT (`apps/api/src/access/audit.service.ts`): every answer of `POST /access/check` (allow, deny, core unreachable) is stored with tenant (from the token), caller, principal, action, resource, reasons, activation seq and commit, source (http/grpc); `GET /tenants/:t/audit` reads one tenant (token tenant must match, 403 otherwise; no token 401). PostgreSQL table `decision_audit` when `IAM_PG_URL` is set (restart-survival tested on real PostgreSQL), in-memory fallback otherwise (NOT durable). Context values are not stored. Limits: only decisions that go through this API are audited (not direct calls to the core), no retention/tamper-proofing/export. Also fixed: the API guard re-reads the JWKS once when a signature fails (core restart with a new key). Tests: `audit.e2e.spec.ts`.
Slices 2 and 3 are built (local, fictional, nothing leaves the machine): `apps/api/src/effects/`. On each activation event (NATS, idempotent consumer) the role diff between this and the previous applied activation produces (a) a NOTIFICATION to a local fictional sink (`POST {IAM_NOTIFY_SINK_URL}/notify`, addressed to `manager-of:<subject>`, nobody is contacted) and (b) OUTBOUND PROVISIONING to a local demo target (`PUT|DELETE {IAM_PROVISION_TARGET_URL}/Users/:id/Roles/:role`, SCIM-LIKE, not the SCIM protocol). Both carry an `Idempotency-Key` = tenant:seq:kind:subject:role:change, are recorded in the PostgreSQL ledger `effects` (done/failed, attempts), are never repeated once done, and a failure throws so the NATS consumer rolls back and retries by redelivery. Targets must be loopback http URLs (anything else is refused). Opt-in at runtime: `IAM_EFFECTS=1` + `IAM_PG_URL` + `IAM_NATS_URL` + the target URLs. Tested in `effects.e2e.spec.ts` (6 tests: real PostgreSQL ledger, real NATS consumer incl. duplicate event and one failing delivery, local HTTP fakes; non-loopback refused; target down then retry). Also tested, with NO stub, in `effects-wiring.e2e.spec.ts` (4 tests): the real Nest `EffectsService` lifecycle driven only by the environment, real Dolt commits exported by `DoltService`, real PostgreSQL journal/outbox, real core, real NATS, local sink and target started by the test (grant and revoke from two real commits, two injected sink failures retried, 8 effects all done with one call per key, outbox re-sent without repeating any effect, non-loopback refused; the replay test cannot tell whether NATS or the ledger dropped the duplicate, only that no effect repeated). NOT tested: effects on real LDAP or a real SCIM server (none exist), single instance only.
Absent from the demonstrated path (not reduced from the request, not built yet): standard OIDC (the IdP is an OAuth/OIDC-inspired prototype: JSON endpoints plus a browser code+PKCE flow, see below); an autonomous agentic runtime (only the bounded demo below exists); a real external effect behind the consumer (effects go to local loopback demo targets only).

## Authority boundary (corrected after review)
`/access/check` and agent delegations take subject and tenant from the VERIFIED token. A body `principal` other than `User::"<sub>"` or another tenant is 403. `roles`, `sod_conflict` and `tenant_mode` from a caller are dropped; the core computes them from the ACTIVE data version (no active version = deny). Other context keys are passed through as UNTRUSTED. Deciding as another identity or with caller-chosen attributes exists only on `POST /access/simulate`, which needs a valid token AND the `x-api-admin-token` header equal to `IAM_API_ADMIN_TOKEN` (16+ chars, disabled when unset); it never runs a tool and is audited with source `simulate`. Tested locally: `agent.e2e.spec.ts` (allow, SoD deny from server data, impersonation and forged attributes, simulation capability, allowlist, TTL, call budget, core down audited), `audit.e2e.spec.ts`, `e2e.spec.ts` (simulate path). The tools `read-report` and `approve-payment` are SIMULATED (no real side effect). The `demo.cedar` static rules for alice/bob only apply to simulation (demo mode).

## Local use
Full step-by-step guide (Windows PowerShell and bash, prerequisites, configuration, start, checks, troubleshooting):
[docs/local-setup.md](docs/local-setup.md). Short version, from the repository root:
1. Prerequisites: Docker (Compose v2), Node.js 22+, Rust stable (on Windows also the MSVC C++ Build Tools).
2. `cp .env.example .env` (PowerShell: `Copy-Item .env.example .env`) and optionally change the placeholder values (never commit `.env`).
3. Build once: `cd core && cargo build -p iam-core`, `cd apps/api && npm ci && npm run build`, `cd apps/web && npm ci`.
4. Infrastructure: `docker compose --env-file .env -f infra/docker-compose.yml up -d` (Dolt seeded with the demo data on 3307,
   PostgreSQL 5433, Temporal 7233, NATS 4222, OpenBao 8200). Started on a Windows 11 + Docker Desktop machine (2026-10-28): all 6
   services running, Dolt seed present.
5. Core: `cd core && IAM_CORE_ADMIN_TOKEN=local-demo-admin-token cargo run -p iam-core` (127.0.0.1:8081).
6. API: `cd apps/api && IAM_CORE_URL=http://127.0.0.1:8081 IAM_ISSUER=http://127.0.0.1:8081 IAM_CORE_ADMIN_TOKEN=local-demo-admin-token DOLT_PASSWORD=<DOLT_ROOT_PASSWORD> IAM_PG_URL=postgres://postgres:<RUNTIME_PG_PASSWORD>@127.0.0.1:5433/runtime node dist/main.js` (port 3000;
   verified against the compose containers: `/health` ok, business routes 401 without a token).
7. Console: `cd apps/web && npx ng serve`, open http://localhost:4200 (build verified on Windows).

See [docs/explorer.md](docs/explorer.md) for the Dolt database explorer (branches, diff, history, SQL, pull requests).
