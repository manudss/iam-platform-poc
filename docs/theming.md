# Theming rules: customisation, CSS variables, light and dark

Every screen of the product must follow the customisation (primary and accent colours, light and dark mode).
This page is the rule book for people and for coding agents (see `.claude/skills/theming/SKILL.md`).
Design background: [branding.md](branding.md).

## How a colour reaches the screen

1. The Customisation page stores two source colours: `primaryColor` and `accentColor` (plugin `branding-base`).
2. `apps/api/src/branding/theme-engine.ts` derives every colour of the interface from them (Material You tonal
   palettes, HCT). HCT tone is CIELAB lightness (L*), so a tone number is also a lightness step.
3. The API serves the result as `theme.css`: `:root` (light), `:root[data-theme='dark']` and the
   `prefers-color-scheme` fallback. Offline defaults live in `apps/web/src/styles.css` and
   `core/crates/iam-core/src/branding-default.css`; both are GENERATED by `node scripts/branding-defaults.mjs`
   (run `npm run build` in `apps/api` first). Never edit the generated block by hand.
4. Components only read `var(--name)`. The hue always follows the accent chosen in Customisation; nothing is
   hard-coded to violet.

## Rules

- No colour literal in components: no `#hex`, `rgb()`, `hsl()`, no named colours, in CSS, templates, inline styles,
  TypeScript and plugin screens. Use a variable of the contract (`THEME_VARIABLES` in `theme-engine.ts`).
  `apps/api/src/branding/css-contract.spec.ts` fails the build otherwise.
- Need a new colour role? Add it to `THEME_VARIABLES` and to BOTH modes in `modeVars`, regenerate the defaults,
  add its contrast pairs to `contrast.spec.ts`. Do not add a local colour.
- Translucent or derived shades: `color-mix(in oklab, var(--accent) 20%, var(--card))`, never a literal.
- Light AND dark: check every new screen in both (`document.documentElement.dataset.theme = 'dark'`), and with at
  least two accents (the default violet and a very different one, for example teal `#00695c`/`#4db6ac`).
- Text must be AA (4.5:1) on every surface it can sit on, including `--row-hover`, `--field-bg`, `--code-bg`;
  borders and field outlines at least 3:1.
- Images and icons that carry colour use the logo/branding endpoints or `currentColor`, not fixed fills.

## Dark palette (validated 10 Nov 2026)

Surfaces climb a visible lightness ladder (tone = L*): `--bg` 16, `--panel` 20, `--card` 25, `--field-bg` 28,
`--code-bg` 30, `--row-hover` 32. Borders (`--line`, `--field-line`) sit at tone 60 to 61 so they read as 3:1 or more
against cards. `--card` over `--bg` is at least 1.3:1. Muted text is tone 80, ink is tone 90. Sidebar and active
states are deep shades of the primary colour. The surface tint comes from the primary hue at low chroma, so it
follows Customisation.

`contrast.spec.ts` checks all of this for nine source-colour pairs (extremes included). If you change a tone,
the spec tells you what broke.

## Checklist for a UI change

1. Only `var(--...)` colours. 2. `npm test` in `apps/api` (contract, contrast). 3. Look at it in light and dark.
4. Look at it with a second accent. 5. Keep text AA and borders visible.
